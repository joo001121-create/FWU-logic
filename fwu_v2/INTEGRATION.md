# 실장 전 연결 조건

## 1. 현재 제공 범위

이번 결과물은 실행 분기와 관제점 정의를 갖춘 **F8 제어 로직 초안**이다. 제조사 레지스터 주소와 신형 IO 모듈 설정을 확정하지 못했으므로 다음 항목이 완료되기 전에는 실장 완료로 판단하지 않는다.

| 항목 | 현재 상태 | 필요한 작업 |
|---|---|---|
| PICV AO3 | 기존 AO3 제어점 이름과 출력 로직 유지 | 새 Combined IO의 실제 주소, 2~10 V 설정과 % 환산, 병렬 입력 부하 확인. 기존 XML은 0~10 V이며 그대로 실장하지 말 것 |
| PICV CH3 | 제어용 수신 인터페이스만 구현 | Belimo Modbus 주소·레지스터·자료형·배율과 실제 DDC read 품질 판정을 연결 |
| 팬 CH1 | 기존 팬 CH1/CH2 맵 보존 | HW 확인에 맞춰 팬 8대의 CH1 주소·포트 배치와 충돌 검증 |
| ATS | 기존 통신점과 알람 유지 | 새 DI 방식과 SuperCap 입력 등 후속 HW 범위 확정 |
| 누수 입력 | 기존 `FWU_LEAK DETECT` 미정의 상태가 남음 | 실제 DI 주소 확인 후 정의. 시험에서는 이 입력만 가상 제공 |
| 외부 상위 통신 | HB·센서 처리와 설정점 추가 | HMI/BMS 읽기·쓰기 맵 연결. 기존 외부맵은 자동 확장하지 않았음 |
| DDC | 보조 로직 5개 등록 | 엔진의 블록 수·ID·실행 순서, 타이머 분리 확인 |

기존 단일 `FWU_PICV FEEDBACK`, `FWU-Flow.Rate`는 v2 제어·알람에서 더 이상 읽지 않는다. 기존 물리·외부맵에는 남아 있으므로 새 맵 작성 시 폐기/미사용 처리하고 HMI에서 유효한 신형 계측값처럼 표시하지 않는다.

## 2. PICV 수신 인터페이스

주소가 미확정인 상태에서 임의의 Modbus 레지스터를 XML에 넣지 않았다. 대신 아래 VP는 **DDC 내부의 임시 전달점**으로 정의했다. 센서가 가상이라는 뜻이 아니다. 실제 CH3 입력을 받는 어댑터 구현은 아직 없다. 레지스터 연결 후 직접 Modbus 점을 사용하는 구조로 바꾸거나 이 전달점을 유지할 수 있다.

밸브 번호 n은 1~4다.

| 점 이름 | 의미 / 단위 | 작성 주체 |
|---|---|---|
| `VP_FWU_PICV-n Position` | 실제 개도 0~100% | CH3 수신 어댑터 |
| `VP_FWU_PICV-n Flow` | 유량 L/min | CH3 수신 어댑터 |
| `VP_FWU_PICV-n Temperature` | 해당 장치 위치의 물 온도 ℃ | CH3 수신 어댑터 |
| `VP_FWU_PICV-n Input OK` | 최신 계측 세트의 통신·자료형·값 품질 정상 여부 | CH3 수신 어댑터 |
| `VP_FWU_PICV-n Sample Seq` | 실제 계측 세트 수신 완료 때마다 바뀌는 번호 | CH3 수신 어댑터 |
| `VP_FWU_PICV-n Sample Prev` | 마지막 처리 번호 | PICV Feedback |
| `VP_FWU_PICV-n Feedback Valid` | 새 데이터 수신 및 신선도·개도 범위 확인 | PICV Feedback |
| `VP_FWU_PICV-n Comm Fault` | 미연결·수신 중단·입력 품질 이상 | PICV Feedback |
| `VP_FWU_PICV-n Alarm` | 수신/품질 이상 또는 적용 가능한 밸브 이상 | PICV Feedback |

어댑터는 데이터를 먼저 쓴 뒤 마지막에 Sample Seq를 바꾼다. **같은 개도값을 다시 받았어도 정상 응답이 새로 있으면 Seq를 바꿔야 한다.** 반대로 DDC가 오래된 캐시를 읽었다는 이유만으로 매 스캔 Seq를 바꾸면 안 된다. 실패 시 Input OK를 0으로 내린다. DDC가 같은 계측 세트를 일관되게 읽도록 실행 순서와 업데이트 원자성을 확인해야 한다.

현재 `Input Enable=0` 기본값에서 네 밸브의 유효성·전체 닫힘은 0이고 수신 이상 알람이 표시된다. 정상 샘플을 받은 뒤에도 Seq가 10초 초과 동안 바뀌지 않으면 무효화한다. 이 10초는 v1의 유량계 감시를 참고한 임시 구현값이며 실제 폴링 주기에 맞춰 확인한다. 데이터 초기값 0을 밸브 닫힘으로 해석하지 않는다.

`Comm Fault`는 지금 단계에서 정확한 고장 원인이 아니라 수신값 사용 불가를 뜻한다. 전원 상실·통신선 단선·값 범위 오류를 구별하는 제조사 진단은 미구현이다. 필요하면 실제 코드표 연결 후 상태점을 구분한다.

## 3. PICV 제어 모드와 알람

| 설정 | 값 | 적용 |
|---|---|---|
| `VP_FWU_PICV Control Mode` | 0 기본 | 적용 모드 미확정. 명령-개도 편차 검사 안 함 |
| 위 설정 | 1 | 위치 제어. 기존 ±30% 범위 밖 40초 초과 편차 검사 |
| 위 설정 | 2 | 유량 제어. 명령율과 개도율 비교 안 함 |
| `VP_FWU_PICV Flow Check Enable` | 0 기본 | 밸브별 유량 기준 미확정. 저유량/패싱 검사 보류 |
| 위 설정 | 1 | 기존 열림 30%·저유량 30 L/min, 닫힘 1%·통과유량 10 L/min 기준 사용. 실제 설계 유량에 맞게 설정값 확인 필수 |

위 모드 VP는 **진단 로직이 어떤 비교를 할지 지정하는 값**이다. 이 VP를 바꾼다고 실제 Belimo의 운전 모드가 바뀌지 않는다. Belimo 설정과 일치시켜야 한다. 유량 모드용 목표-실측 유량 편차 알람은 V'max·유량특성·허용편차 확인 후 별도 결정한다.

`Monitor Ready`는 네 입력이 유효하고 진단 설정이 지정됐음을 나타내는 최소 상태점이다. 전체 고장 진단의 완전성을 보장하지 않는다. 특히 유량 모드의 명령 추종 진단은 미구현이다. HMI에서는 알람 0만 보고 ‘진단 정상’이라고 표시하지 않는다.

실제 개도 4개가 모두 유효하고 각각 5% 미만일 때만 `All Closed=1`이다. 일부 수신 실패 또는 미폐쇄에서는 정상 정지가 계속 대기한다. 비상 P1 및 원격 P2의 출력 강제는 이 대기를 따르지 않는다.

## 4. 상위·외부 센서와 HMI

- `Upper Comm Enable` 기본 0, 종류별 Count 기본 0. 실장 초기 설정에서 상위가 있으면 감시를 켜고 실제 센서 수와 통신맵을 맞춘다.
- Enable=0이면 통신 알람을 해제하고 HB 이전값·타이머를 동기화한다. 다시 켤 때 30초 기본 유예를 새로 시작한다. 감시 중 알람은 HB 복구만으로 해제하지 않고 Reset이 필요하다.
- 외부 CZT/HZT/RDP는 감시 미사용 때 PV Valid=0이다. CZH는 합의대로 기존 유효성 정책을 유지하며 Count만 적용한다.
- Count는 0~10 정수, HB/수신 Timeout은 양수, 댐퍼 지연은 0 이상으로 입력하도록 UI를 제한한다. XML min/max만으로 실제 UI 입력 제한이 보장된다고 가정하지 않는다.
- 팬 모드는 정수 0~4, 수동 속도는 정지 0 또는 설정 최소~최대 범위. 최소가 최대를 넘는 설정을 막는다. 수동 출력의 새 코드 클램프는 추가하지 않았다.
- `SF Count` VP는 이전 인터페이스 보존용이다. F8 고장 집계는 코드 상수 8을 사용하며 이 VP만 변경해서 F4/F6로 바뀌지 않는다.
- 새 관제점 ID와 주소는 저장소 내 중복을 피한 초안 할당이다. DDC 도구에서 지원 범위, 생성/가져오기, 실제 backup/default 동작을 확인한다. 제조사 통신 주소와는 다르다.

## 5. 회사 PC 시험

1. 새 물리 맵·수신 어댑터·누수 DI 연결 및 외부 공개점을 완성한다.
2. `READPOINT_ALARM`, `WRITEPOINT_PRI` 등 기존 코드의 API와 해당 펌웨어의 실제 지원명을 확인한다.
3. 동일 출력점에 모드별 LOOP2 ID를 쓰는 v1 방식을 유지했으므로, 엔진에서의 상태 분리·초기화를 확인한다.
4. 전원 재투입·DDC 이중화 절체에서 전달점의 초기화와 유효성, 우선순위 잔존값, 타이머 동작을 확인한다.
5. 정상/고장/복구, 미폐쇄 대기, 비상·원격 강제, 팬 AO 전환을 실제 신호와 함께 시험한다.
6. SAT PI·팬 PI 응답, ΔT -2 임시값, 팬 최소 30%, 새 팬 환산값을 팬/HW 개발팀과 검증한다.
